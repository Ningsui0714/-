# 三工作流与项目 Agent 数据传递说明

## 0. 项目 Agent 对接（推荐入口）

Agent 页面使用项目级 API 保存目标、学习路径、测评会话、章节教学和项目笔记。所有项目接口都必须带 `student_id`；项目级接口还必须使用路径中的 `project_id`，后端会校验学生与项目归属。

### 0.1 创建与读取项目

```http
POST /api/projects
Content-Type: application/json
```

```json
{
  "student_id": "STU-001",
  "text": "六周内掌握 Python 数据分析并完成销售数据看板",
  "defer_planning": true
}
```

成功返回的 `project` 至少包含 `project_id`、`goal_name`、`diagnosis_state`、`planning_state`、`support_level`、`assessment_state`、`goal_constraints`、`weak_point_count` 和 `progress`。

Agent 对话建项使用 `defer_planning=true`。此时只保存已澄清的目标和待确认能力范围，返回 `planning_state="awaiting_learner_profile"`，`learning_path.items` 及 `learning_plan` 均为空；前端必须先展示当前基础和熟悉知识点问卷，不得提前显示候选路径、学习地图或计划。兼容旧调用时可不传该字段，后端仍按原方式立即生成路径。

问卷提交后才生成首版个性化路径：

```http
POST /api/projects/{project_id}/assessments/intake
Content-Type: application/json
```

```json
{
  "student_id": "STU-001",
  "self_reported_level": "zero_foundation | basic | experienced | uncertain",
  "claimed_knowledge_point_ids": ["KN-..."]
}
```

成功后返回 `planning_state="ready"` 和 `learning_path_generated=true`，并原子写入 `learning_path`、首版 `learning_plan`、章节缓存任务及后续题目生成任务。熟练度与自述知识点只调整路径节奏、讲解重点和预计时长，不会写成已掌握，也不能解锁前置知识；掌握度仍只接受正式测评证据。

选择 `self_reported_level="zero_foundation"` 时是例外：返回 `initial_assessment_state="awaiting_practice"`、`should_start_initial_assessment=false`，不生成或启动初始测评题单，直接进入基础优先学习与零基础基线讲解；后续练习和阶段检查仍可在学习过程中提供，但不会把零基础自述写成掌握度证据。非零基础仍按正式能力包启动 `initial_diagnostic`，候选方向按 `provisional_self_check` 规则处理。

### 0.1 学习路径编排

学习路径采用参考 EduAgents 的“结构化知识点 + 显式前置 DAG”方法：每个节点保留稳定 `knowledge_point_id`、`learning_outcome`、`prerequisites`、`stage_id` 和 `is_target`。后端先校验知识点 ID、前置引用与无环依赖，再进行稳定拓扑排序；阶段只用于展示和计划分组，绝不根据阶段或排列顺序自动补造前置关系。阶段顺序还必须不早于任一前置节点，避免“实践前置被排到综合应用、依赖节点却仍在核心学习”的倒序。基础准备由无前置节点组成，核心学习保留中间依赖节点，实践/项目/评估节点及目标叶子进入综合应用。学习计划复用这些 `stage_id`，并继续以用户声明的周期和每日时长作为总时长硬约束。

目标无法可靠归一化时不创建项目，返回：

```json
{
  "status": "needs_clarification",
  "clarification": "请补充更具体的学习目标。",
  "missing_fields": ["target_outcome"],
  "reason": "goal_unclear"
}
```

```http
GET /api/projects?student_id=STU-001
GET /api/projects/{project_id}?student_id=STU-001
```

详情中的 `learning_path.items[]` 是当前项目独立的路径；每项包含 `knowledge_point_id`、`knowledge_point_name`、`recommended_order`、`status`、`mastery`、`prerequisites`、`goal_connection`、`learning_outcome`、`source_status` 和章节生成状态。项目之间不共享测评会话、薄弱点或路径状态。

### 0.2 正式能力包与候选路径边界

`support_level="validated_graph"` 且 `assessment_state="ready"` 表示已接入正式能力包，可以在完成初始能力问卷后开始正式目标诊断。未接入正式能力包的目标使用 `support_level="generated_scaffold"` 和 `assessment_state="question_sources_pending"`，只能提供参考规划或 `provisional_self_check` 临时自检，不得宣称为正式能力诊断。两类目标在对话建项后都先经历 `planning_state="awaiting_learner_profile"`，问卷提交后再切换为 `ready`。

候选路径由 AI 生成、后端确定性校验。校验包括：节点数量 4-20、节点和知识类型合法且不重复、不得使用泛化占位名称、每个节点都必须在 `goal_connection` 中说明与用户目标的直接关系、前置依赖必须存在且无环。任何节点不相关都会导致整条候选路径被拒绝；后端不会把候选内容直接写入权威知识库。

### 0.3 学习计划、地图与版本

项目学习计划、学习地图和计划说明均以项目当前学习路径和**正式测评证据**为依据。学习者自评、完成计划步骤或阅读 AI 讲解不构成掌握度证据；未评估知识点以 `mastery: null` 表示，不能当作 0 分或技能缺口。只有一次正式答对的节点会保留 `evidence_status: "candidate"`、现有 `mastery` 与 `source_event_ids`，对外显示为“待验证”，既不视为已掌握，也不归为未评估。

```http
GET /api/projects/{project_id}/plan?student_id=STU-001
GET /api/projects/{project_id}/learning-map?student_id=STU-001
GET /api/projects/{project_id}/plan-brief?student_id=STU-001
```

`/plan` 返回当前 `learning_plan`。计划包含稳定的 `plan_id`、递增的 `plan_version`、生成依据摘要的 `context_hash`、`generated_at`、三个顺序阶段 `foundation` / `core` / `application`、每步预计时长和前置依赖，以及 `recommended_step`、进度和 `time_budget`。当用户声明学习周期与每日时长时，`daily_schedule` 会从已校验的步骤确定性拆分出每日学习、最小实践和检查任务；每天不超过预算，全部步骤时长必须被完整排入。正式证据已验证的节点以 `verified_fast_track` 压缩为快速确认，待补强节点以 `evidence_repair` 延长并优先复习，`candidate` 节点以 `candidate_confirmation` 安排确认性学习。前端应把 `plan_version` 作为当前版本标识，不要自行推算版本号。

`/learning-map` 是只读投影，返回 `nodes`、`edges`、`current_recommended_kc`、`recommended_candidates`、`locked_nodes` 和 `active_path`；它不修改能力图谱或项目状态。`/plan-brief` 返回面向学习者的确定性说明，包括已掌握、需补强、待验证、未评估、关键路径、阶段概览和适应规则，不暴露内部规则码或原始状态 JSON。

学习者可显式请求生成新版本：

```http
POST /api/projects/{project_id}/plan/regenerate
Content-Type: application/json
```

```json
{
  "student_id": "STU-001"
}
```

系统也会在正式测评证据或已声明的学习时间预算改变计划上下文时，尝试生成新版本。候选版本必须先通过结构、三阶段顺序、目标知识点覆盖、可检查学习目标、步骤与时长、前置依赖/环路与拓扑顺序、每日执行安排和时间预算校验，才会原子切换为当前计划；校验失败时保留现有版本并返回 `PLAN_REGENERATION_REJECTED`（HTTP 409）。被替换的计划保存在项目状态的 `learning_plan_history`（最多 5 个），用于追溯，不是对外主读取接口。

切换成功后，后端只将该项目的章节讲解缓存重置为待生成，并按新计划后台准备章节。正式测评证据、作答记录、掌握度、项目笔记和其他学习数据均不会删除。计划步骤的 `completed` 仅推进计划进度，不能直接更新掌握度或写入正式画像。

### 0.4 项目测评

正式目标诊断和阶段检查使用同一套测评会话接口；`diagnosis/*` 是首轮诊断兼容别名，`assessments/*` 是统一入口：

```http
POST /api/projects/{project_id}/diagnosis/start
POST /api/projects/{project_id}/assessments/start
```

其中 `diagnosis/start` 固定创建 `initial_diagnostic`，仅用于兼容旧 Agent 页面；需要指定 `stage_check`、`self_check` 或 `provisional_self_check` 时使用 `assessments/start`。

```json
{
  "student_id": "STU-001",
  "assessment_type": "initial_diagnostic",
  "knowledge_point_id": "可选；阶段检查时指定"
}
```

支持的 `assessment_type`：`initial_diagnostic`、`stage_check`、`self_check`、`provisional_self_check`。返回 `assessment_id`、`provider`、`blueprint`、`source_policy`、不含答案和解析的 `questions`、`total`。候选目标只能使用 `provisional_self_check`，其结果不写入正式画像、不更新掌握度、不改变路径。

```http
POST /api/projects/{project_id}/diagnosis/answer
POST /api/projects/{project_id}/assessments/answer
```

```json
{
  "student_id": "STU-001",
  "assessment_id": "ASSESS-001",
  "selected": "b",
  "skipped": false
}
```

每次作答只提交当前选项（`a`/`b`/`c`/`d`）或 `skipped=true`。正式测评作答会落库为证据并按知识点聚合薄弱点；末题完成后返回 `summary`，项目详情中的 `weak_points` 随之更新。

### 0.5 章节教学、消息和笔记

```http
POST /api/projects/{project_id}/explain
Content-Type: application/json
```

```json
{
  "student_id": "STU-001",
  "knowledge_point_id": "KN-CUSTOM-001"
}
```

章节在项目创建后后台预生成。读取尚未完成时返回 `status="preparing"`、`generation_status` 和 `retry_after_ms`，客户端应稍后重试；就绪后返回 `content_blocks`、`resources`、`source_references` 等教学包字段。项目讲解会使用缓存结果，不应在详情 GET 中自行重新规划路径。

```http
GET /api/projects/{project_id}/messages?student_id=STU-001
GET /api/projects/{project_id}/notes?student_id=STU-001&knowledge_point_id=KN-...
POST /api/projects/{project_id}/notes
POST /api/projects/{project_id}/notes/delete
POST /api/projects/{project_id}/delete
```

保存笔记至少需要 `student_id`、`knowledge_point_id` 和 `note_markdown`；知识点必须属于当前项目。普通笔记上限 8,000 字。章节编辑器使用 `tags:["lesson_document_override"]` 保存覆盖稿，上限 100,000 字；首次可省略 `note_id`，后端按项目、学生、知识点和该标签幂等定位并返回正式 `note_id`，后续保存应复用它。保存失败时客户端保留草稿并重试，不应生成新的笔记 ID。

### 0.6 删除和错误处理

项目/笔记删除只影响当前 `student_id` 所属数据。常见错误码包括 `PROJECT_NOT_FOUND`、`KNOWLEDGE_POINT_NOT_FOUND`、`GOAL_ASSESSMENT_SOURCE_PENDING`、`ASSESSMENT_QUESTION_GAP`、`ASSESSMENT_SESSION_MISMATCH` 和 `NOTE_NOT_FOUND`；客户端应展示后端 `message`，不得将失败响应伪装成成功或补造题目、来源和视频。

## 1. 首次数据来自上游

测验系统或诊断模块把完整结果发送给后端：

```http
POST /api/upstream/assessment-result
Content-Type: application/json
```

```json
{
  "student_id": "STU-001",
  "session_id": "SESSION-001",
  "event_id": "ASSESSMENT-RESULT-001",
  "training_cycle_id": "可选，由后端补齐",
  "learning_task_id": "可选，由后端补齐",
  "task_instance_id": "可选，由后端补齐",
  "question_instance_id": "可选，由后端补齐",
  "attempt_id": "ATTEMPT-001",
  "learning_goal": {
    "goal_id": "GOAL-PY-001",
    "goal_name": "完成 Python 成绩统计实训"
  },
  "question_snapshot": {
    "question_id": "Q-003",
    "question_text": "缺考不参与平均分计算，请计算有效成绩平均分。"
  },
  "current_attempt": {
    "student_answer": "(90+60)/3=50"
  },
  "validated_evaluation": {
    "validation_passed": true,
    "evaluation_status": "incorrect",
    "error_points": [
      {
        "error_id": "PY_AGG_INVALID_DENOMINATOR",
        "knowledge_point_id": "KN_PY_AGGREGATE",
        "knowledge_point_name": "平均分与统计口径",
        "student_evidence": "分母使用总人数3",
        "expected_behavior": "分母使用有效成绩数量2",
        "root_cause": "统计口径不一致"
      }
    ]
  },
  "diagnostic_result": {
    "weak_points": [
      {
        "knowledge_point_id": "KN_PY_AGGREGATE",
        "knowledge_point_name": "平均分与统计口径",
        "knowledge_type": "conceptual",
        "mastery": 42,
        "priority": 90,
        "recommended_order": 1
      }
    ]
  },
  "current_knowledge_point": {
    "knowledge_point_id": "KN_PY_AGGREGATE",
    "knowledge_point_name": "平均分与统计口径",
    "mastery": 42
  }
}
```

后端按场景组织三工作流输入：

- `validated_evaluation.evaluation_status == "incorrect"`：设置 `route_type="error_remediation"`，生成测验纠错讲解；
- `diagnostic_result.weak_points` 非空：设置 `route_type="first_learning"` 并补充 `event_type="initialize_learning"`，生成连续学习讲解；
- 两类数据同时存在时，分别请求学习 Flow 和纠错 Flow；画像 Flow 由后端按累计事件数异步触发。

写入后端时会建立 `training_cycle_id → learning_task_id → task_instance_id → question_instance_id → attempt_id → explanation_session_id` 的业务链路。迁移期仍保留 `student_state` 作为前端启动缓存。

`event_id` 是上游结果的幂等键。同一个 `event_id` 重复提交时，后端返回 `status=duplicate`，不更新学生状态、不累计画像事件数，也不再次调用学习或纠错工作流。

## 2. 后端发送给星辰

三个工作流共用星辰 OpenAPI，但使用各自的 `flow_id`：

```http
POST https://xingchen-api.xf-yun.com/workflow/v1/chat/completions
Authorization: Bearer API_KEY:API_SECRET
Content-Type: application/json
```

```json
{
  "flow_id": "XINGCHEN_PROFILE_FLOW_ID | XINGCHEN_LEARNING_FLOW_ID | XINGCHEN_REMEDIATION_FLOW_ID",
  "uid": "STU-001",
  "parameters": {
    "AGENT_USER_INPUT": "{完整业务JSON序列化后的字符串}"
  },
  "stream": false
}
```

`AGENT_USER_INPUT` 不是一句自然语言，而是完整业务 JSON 的字符串。画像 Flow 接收聚合历史；学习和纠错 Flow 接收后端组装的 `context`、`strategy`、`student_profile` 和 `kb_text`。策略选择和知识依据缓存均在后端完成。

## 3. 学习过程中的前端事件

前端不需要每次重复发送全部诊断数据，只发送当前动作：

```http
POST /api/workflows/learning
```

```json
{
  "student_id": "STU-001",
  "session_id": "SESSION-001",
  "event_type": "switch_explanation",
  "previous_mode": "interactive_document"
}
```

后端从 SQLite 读取该学生的目标、薄弱点、路径和教学历史，合并为完整 JSON 后再调用学习工作流。

支持事件：`initialize_learning`、`continue_learning`、`show_example`、`show_steps`、`switch_explanation`、`request_video`、`request_text`、`check_feedback`。

新前端优先使用统一入口：

```http
POST /api/explanations
```

```json
{
  "student_id": "STU-001",
  "session_id": "SESSION-001",
  "scene": "re_explain",
  "source_explanation_session_id": "EXPLAIN-001",
  "question_instance_id": "QUESTION-001",
  "attempt_id": "ATTEMPT-001",
  "requested_delivery_mode": "video"
}
```

`learn`、`re_explain` 和 `error_correction` 分别路由到学习或纠错工作流；`stage_error`、`prerequisite` 仍返回 `status=not_implemented`、`code=SCENE_NOT_READY`。

画像可通过 `GET /api/admin/profile-status?student_id=...` 查询，也可通过 `POST /api/admin/refresh-profile` 同步强制刷新。常规请求中的画像刷新在后台执行，不阻塞学习或纠错响应。

## 4. 测验异常追问与恢复

测验讲解工作流缺少题目或作答内容时返回：

```json
{
  "status": "needs_clarification",
  "clarification_question": "请补充本次题目描述。",
  "resume_token": "随机、短期、一次性恢复令牌"
}
```

前端提交补充内容：

```http
POST /api/workflows/review/resume
```

```json
{
  "student_id": "STU-001",
  "session_id": "SESSION-001",
  "resume_token": "上一轮返回的令牌",
  "clarification_reply": "完整题目描述"
}
```

用户无法提供时，`clarification_reply` 传入“无法提供”，工作流返回 `ended_by_user`。

mock 模式只在数据库中保存恢复上下文，浏览器拿到的令牌不包含题目或作答正文；令牌与首次请求的 `student_id`、`session_id` 绑定，且使用后立即失效。身份不匹配的请求不会消耗原令牌。

## 5. 接口访问边界

后端默认只监听 `127.0.0.1`，跨域响应仅允许 `APP_ALLOWED_ORIGINS` 白名单中的来源。`GET /api/health` 保持公开；设置 `APP_API_TOKEN` 后，其余 `/api/*` 请求必须发送 `Authorization: Bearer <token>`。监听非回环地址时，后端会拒绝在未配置 `APP_API_TOKEN` 的情况下启动。

## 6. 星辰结果回到前端

非流式响应中的工作流结果位于 `choices[0].delta.content`。后端将其中的 JSON 解析、保存到 SQLite，再返回前端。

前端根据以下字段选择页面组件：

- 学习结果：`teaching_plan`、`content_blocks`、`resources`、`path_update`；
- 测验结果：`personalized_explanation`、`target_error`、`retry_guidance`；
- 通用状态：`status`、`resume_token`。

后端还会附加 `task_instance_id`、`question_instance_id`、`attempt_id`、`explanation_session_id`、`scene`、`explanation_type`、`explanation_mode`、`delivery_mode` 和 `source_references`。

## 7. 重做和变式题

`POST /api/practice/questions` 使用 `mode=retry_original|variant` 创建新的 `question_instance_id`，响应包含题干和 `answer_schema`。前端据此显示输入区。

`POST /api/question-instances/{id}/attempts` 创建新的 `attempt_id` 并返回判定结果。答错时响应包含 `explanation_input`，前端将其提交到 `scene=error_correction`，形成“生成题目 → 作答 → 判定 → 纠错讲解”闭环。

## 8. 联网视频搜索与来源

学习初始化、请求视频、切换讲法和测验讲解进入后端后，后端按当前知识点生成视频检索词，通过 Bing RSS 搜索白名单教育视频站点。搜索结果写入工作流输入：

```json
    "status": "ok",

    "query": "平均分与统计口径 教学 视频",
    "searched_at": "2026-07-29T17:00:00+08:00",
    "results": [
      {
        "type": "video",
        "title": "视频标题",
        "url": "原始视频页面地址",
        "embed_url": "允许内嵌时的播放器地址",

        "source_domain": "来源域名",
        "provider": "Bing RSS",
        "snippet": "搜索摘要"
      }
    ]
  }
}
```

后端会把可核验视频合并到学习和纠错两个讲解工作流的 `resources` 中。前端必须同时展示 `title`、`source`、`provider` 和原始 `url`；没有可核验结果时展示 `resource_gap`，不能使用虚构视频链接或模拟播放进度。

讲解完成后，后端将知识库、诊断卡、内容块和联网资源统一转换为 `source_references`，记录标题、文档标识、定位信息、引用文本、URL 和核验状态。前端只在 URL 通过校验且资源存在时显示可点击链接。

## 9. 非正式方向的路径生成门禁

`POST /api/projects` 与 `POST /api/agent/turn` 都先判定目标是否命中已审核能力包。未命中时只能生成 `generated_scaffold` 候选路径，不能产生正式测评、掌握度或画像结论。

- 对嵌入式、人工智能、网络安全等包含多个技术分支的领域，缺少方向时返回 `status=needs_clarification`、`reason=domain_direction_required` 和 `missing_fields=["learning_direction"]`，不创建项目、不输出通用章节。
- 本地候选路径只允许使用已配置的领域分类模板；未知方向在本地 mock 下返回 `reason=capability_taxonomy_required`，提示补齐能力图谱、来源与题库，而非退化为“术语→机制→案例→项目”的泛化链路。
- 候选知识点必须携带 `goal_connection`、`learning_outcome`、`prerequisites`、`source_status`、阶段和目标标记；其中 `source_status=candidate` 明确表示待来源/领域审核。
