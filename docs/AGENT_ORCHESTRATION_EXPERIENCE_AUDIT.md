# 智能体编排与计算机学生体验审计（2026-08-14）

## 结论

LearnFlow 的三类主 Agent、五核写入链、确定性判题和 Remediation 闭环具有正确的
架构边界。本次审计发现的关键体验断点是：用户已经确认路线后，系统会提示“现在可以
进入第一关”，但没有在同一编排事务中真正进入该关卡。这样把一个确定性的状态切换
留给了自然语言，既增加一步等待，也会让学生误以为系统仍在“继续讲下一阶段”。

已修复为：`apply_learning_path` 成功物化路线时，立即复用标准
`checkpoint_entered` 事件链进入首个可用关卡，并把 checkpoint 返回给前端。这个
自动化只限无副作用的上下文切换；讲义、题目和评估仍需用户在关卡内主动开始，绝不把
内容生成或页面访问当作掌握证据。

## 外部证据与调研边界

本次使用公开论文、开发者大样本调查、公开社区索引和中文视频搜索进行交叉查找。研究
结论优先采用原始论文和调查；社区样本仅用于发现体验语言，不能当作普遍比例。Exa 的
免费检索配额在并行检索时触发限流，Reddit 的已登录接口也不可用；因此这是一份
多源、可复查的开放网络样本，不宣称穷尽整个互联网。

| 证据 | 直接信号 | 对 LearnFlow 的编排含义 |
| --- | --- | --- |
| [CS1 中使用 ChatGPT 的受控实验](https://maiziezhoulab.github.io/paper/ICSE-SEET2024.pdf) | 使用者较少探索传统资源，且依赖 ChatGPT 不保证更好的学习表现。 | 默认先保留学生自己的尝试；帮助应以解释、提示和反思为主，而非直接交付解法。 |
| [编程教育中的 GenAI：学生感受与纠错挑战](https://link.springer.com/article/10.1007/s40593-025-00496-4) | 学生认可效率与创造性价值，但纠正 LLM 生成代码明显困难。 | 将 AI 输出视为待审查的候选；把调试、验证和错误定位设计成学习任务。 |
| [学习者与教师对 AI 编程学习工具的共同设计研究](https://arxiv.org/abs/2503.00144) | 学生要及时、贴近代码的支持和自主权；教师担心过载与错误的学生模型。 | 采用“系统提出下一步、学生保留选择”的共享控制；每次只给一个明确动作，并说明原因。 |
| [Stack Overflow 2025 Developer Survey](https://stackoverflow.co/company/press/archive/stack-overflow-2025-developer-survey/) | 高使用率与低准确性信任并存；46% 的开发者不信任 AI 输出准确性。 | 每个代码/工具结果要能追溯、显示状态和失败原因，不能用流畅表述替代可验证结果。 |
| [公开开发者社区对该调查的讨论](https://www.reddit.com/r/programming/comments/1mdyy9x/stack_overflow_survey_2025_84_of_devs_use_ai_but/) | 讨论反复强调 AI “几乎正确”却增加调试成本，且样本与使用场景会影响结论。 | 不把单一社区意见或模型自评当事实；提供测试、来源、置信度和可纠正历史。 |
| 中文视频搜索样本 | AI 编程入门/实战教程有大量观看，但当前无可验证评论数据。 | 中文计算机学生同样需要从“快速做出东西”转向“能解释、测试、迁移”；不以热度推断学习效果。 |

## 计算机学生应该得到的体验

1. **先行动，后叙述状态。** “确认路线”“开始”“进入下一关”等意图应触发确定性
   Action，而不是生成一段要求用户再执行同一动作的文字。
2. **一个可见的下一步。** 每回合最多一个主要动作，清晰显示现在在哪一关、为什么
   到这里、下一步可以做什么；复杂的连续课程不能塞进聊天气泡。
3. **保留认知劳动。** 默认让学生先写、解释、运行或调试；需要帮助时提供逐级提示、
   步骤、示例和对 AI 输出的审查任务，而不是先给完成品。
4. **共享控制而非强推流程。** 系统可以在证据充分时自动完成无副作用导航；会写数据、
   生成昂贵内容、变更文件或调整路线时，必须使用明确确认。
5. **代码学习必须可验证。** 面向当前代码、测试输出和题目规格给反馈；明确区分运行、
   辅助完成、独立正确、原题重做与变式迁移。
6. **可信而可纠正。** 显示来源、任务状态、失败原因和证据的实际含义；AI 生成内容、
   浏览讲义和“我懂了”都不应被说成掌握。
7. **连续但有边界。** 同一项目/关卡保留必要上下文，跨项目不串台；本地代码 Agent
   是 Tutor 的受控工具，先在隔离副本运行，再经第二次确认写回。

## 从入口到证据的审计结果

| 环节 | 实现与结论 | 本次处理 |
| --- | --- | --- |
| 主 Agent 边界 | 注册表保持 Tutor、学习设计、实践验证三类主责任接口；领域 Agent 不夺取用户控制权。 | 通过注册表校验。 |
| 意图到 Action | `process_turn()` 先识别明确意图和待确认 Action，再允许 Tutor 生成自然语言。 | 保持现有“明确命令当轮执行”原则。 |
| 路线确认 | `apply_learning_path` 原本只返回“现在可以进入”。 | 同一事务直接进入首个开放关卡，写入 `checkpoint_entered` 并返回前端导航目标。 |
| 内容生成 | 讲义/评估是异步产物，不能成为掌握证明。 | 自动进入关卡后不自动启动任何生成任务，避免无意义生成和越权消耗。 |
| 实践与纠错 | Attempt、确定性评分和重做/变式链已区分辅助与独立性。 | 未改变证据和 Remediation 语义。 |
| 任务可审计性 | 任务完成器会发出 `source_processed`、`assessment_generated`、`task_completed`、`task_failed`，但部分未登记。 | 新增 `record_task_outcome` capability 和 EventContract；失败只写结构阻塞，生成产物不写掌握。 |
| 前端交接 | TutorPanel 已消费 `result.checkpoint` 并通过 `onCheckpointChange` 打开关卡页面。 | 后端现在稳定提供该结果，端到端闭环成立。 |
| 五核与记忆 | 所有变化仍经 `EvidenceEvent -> reducer -> KernelMutation -> Memory Graph`。 | 自动切换仅影响 `structure`；不新增直接 KernelState 写入。 |

## 变更后的确定性流程

```text
用户确认路线
  -> apply_learning_path 写入并物化路线
  -> 选择首个未完成关卡（确定性）
  -> checkpoint_entered EvidenceEvent
  -> reducer 更新 structure 投影
  -> 返回 checkpoint 给前端并打开关卡
  -> 学生自主选择生成讲义、题目或开始练习
```

该流程的停止点很重要：它不会因为“进入关卡”自动生成下一阶段文本、题目或讲义，更不
会升级掌握。生成、提交、评分、Remediation 和迁移验证仍各自有清晰的授权、事件和
证据语义。

## 后续验证重点

- 用真实学生访谈或可退出的产品内反馈，验证“自动进入首关”是否减少困惑而不降低
  控制感；按新手与高自我效能学生分层观察。
- 为解释/提示/示例记录效果，比较“先尝试再求助”与“直接索要解答”对后续变式迁移的
  影响；不要只优化完成速度或自我感受。
- 将所有历史导入和记忆纠正事件继续补齐到注册表，并用静态/运行时检查防止新事件绕开
  EventContract。
- 为桌面工作区和异步生成任务增加端到端浏览器验收，覆盖任务完成、失败、重试和关卡
  导航的可见状态。
