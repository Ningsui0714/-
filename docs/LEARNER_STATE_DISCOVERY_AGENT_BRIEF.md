# LearnFlow 学习信息快速获取模块：开发 Agent 任务书

> 文档性质：开发 Agent 的完整任务上下文，不是新的架构权威。
>
> 本文只面向负责实现该模块的开发 Agent，用于传递委托人的产品意志、仓库上下文、协作边界和验收目标。若本文与 `ARCHITECTURE_AUTHORITY.md`、`AGENT_ARCHITECTURE_GUIDE.md` 或可执行注册表冲突，以上述权威来源为准。

## 1. 身份与任务

你是 LearnFlow **学习信息快速获取模块（Learner State Discovery）**的开发负责人。你拥有这个模块从产品方案、算法选择、接口设计、后端实现、交互界面到测试与演示的端到端设计权。

这个模块不是普通注册问卷，也不是固定题量的入学考试。它要解决的问题是：

> 在不打断学习动机的前提下，用尽可能少、尽可能自然的有效交互，快速降低系统对学习者状态的不确定性，并把结果变成可验证、可纠正、可持续使用的学习证据。

模块既可以用于首次建立学习项目，也可以在证据不足、目标变化、进入新领域或旧判断失效时再次启动。它应是一种持续能力，而不是只能运行一次的 onboarding 页面。

## 2. 委托人的产品意志

设计和实现时，应优先体现以下取向：

1. **每次交互都应有信息价值。** 不为凑题量而提问，要知道本轮交互希望确认或排除什么。
2. **尽早产生可用信息。** 用户完成第一次有效回答后，系统就应能形成至少一条有限但有依据的观察，不必等待整套流程结束。
3. **允许不知道。** “未知”“证据不足”“需要以后验证”都比虚假的完整画像更有价值。
4. **证据强于标签。** 系统应保留用户做了什么、为什么形成判断，而不只保存“初级”“视觉型”等抽象结论。
5. **学习体验优先。** 用户应感觉自己正在解决有意义的问题、开始学习，而不是接受冗长审问。
6. **准确性来自组合证据。** 自述、客观作答、代码测试、解释理由、独立实践和迁移表现应被区分对待。
7. **状态可以被纠正。** 新证据能够修订旧判断；用户也能查看、确认、反驳或归档错误记忆。
8. **高影响决策应可检查。** 题目选择、评分、追问、停止和证据升级应有策略版本、原因或可重放依据。
9. **外部模型不是前提。** 在线模型可增强生成与表达，但离线 seeded 模式必须能完成核心闭环。
10. **不要为了遵守旧实现而牺牲更好的设计。** 发现现有契约不足时，可以提出明确、可迁移的新契约。

## 4. 现有架构事实

LearnFlow 只有三个主 Agent 责任接口：

- **Tutor Agent**：理解意图、组织对话、控制 Action、协调工作台和能力交接。
- **Learning Design Agent**：产生路线、内容、问题、评估规格和视觉产物。
- **Practice Agent**：处理提交、测试、判题、评估、诊断追问与纠错呈现。

五核是学习者状态维度，不是五个 Agent：

| Kernel | 它回答的问题 | 状态对象 | 不应越界推断 |
|---|---|---|---|
| `structure` | 学习者现在在哪里，怎样离开、继续和返回？ | 项目、检查点、路径依赖、阻塞和返回锚点 | 掌握、目标、情绪或实践能力 |
| `knowledge` | 对哪个知识点理解到什么程度，证据是什么？ | 概念、缺口、错误推理、待解问题和理解状态 | 把接触、自述或一次答错当成长期结论 |
| `human` | 当前怎样教、怎样交互更合适？ | 负荷、注意、情绪反应、节奏和交互偏好 | 从分数推断人格、医学状态或固定学习风格 |
| `value` | 为什么学，当前什么目标和投入更重要？ | 目标、优先级、动机、兴趣和相关性 | 用模型猜测替代用户确认，或当作能力证据 |
| `practice` | 能否独立完成，并迁移到新情境？ | 尝试、辅助等级、产物、反馈和迁移表现 | 把有提示成功或原题重做当成独立迁移 |

五核是决策分工，不是信息标签：`structure` 决定导航，`knowledge` 决定学习/验证对象，`human` 决定交互适配，`value` 决定优先级，`practice` 决定能力验证。一次交互可以形成多个核的事件证据，但每个 `kernel_target` 都必须有独立理由，不能把一个核的结论复制到其他核。

唯一合法的五核状态权威链路是：

```text
用户 / UI / Tool / Agent 行为
  -> EvidenceEvent
  -> five_kernel_reducer
  -> KernelMutation
  -> KernelState
  -> MemoryFact -> MemoryModule -> MemoryClaim
```

模块可以保存诊断会话、题目实例、提交、测试结果、运行缓存和中间计算，但不得建立一套与 Evidence Ledger、KernelState 并列的长期学习者事实权威。

### 五核交互是模块的主循环

五核不只是诊断完成后的写入目标，也应是模块决定“下一步问什么”的主要上下文。模块应形成持续的双向闭环：

```text
读取有 scope 的五核投影与近期证据
  -> 识别已知、未知、冲突和最值得降低的不确定性
  -> 选择问题、任务、澄清或追问
  -> 获得用户行为与可验证结果
  -> 追加规范化 EvidenceEvent
  -> five_kernel_reducer 生成 KernelMutation
  -> 重新读取更新后的五核投影
  -> 继续、提前结束、进入学习或交给 Remediation
```

不要在诊断模块内部计算一份最终画像后一次性覆盖五核。第一次有效交互就可以产生事件；Reducer 更新后，下一轮应尽可能消费新的投影。诊断会话中的临时推测只有在形成合格事件并被归约后，才成为 LearnFlow 可持续使用的状态。

每轮决策前，模块应能够表达：

- 当前五核中已经知道什么；
- 哪些信息只有自述或低置信度证据；
- 哪些信息相互冲突或已经过期；
- 当前最值得确认的是哪一核、哪个 subject；
- 为什么本轮交互比其他候选问题更有信息价值；
- 新证据会影响哪个 Kernel，但不预先伪造 Kernel patch。

五核在本模块中的典型交互方式如下。具体算法和问题形式仍由你设计：

| Kernel | 读取它是为了什么 | 可以形成的事件证据 | 必须避免的误判 |
|---|---|---|---|
| `structure` | 确认当前项目、检查点、路径依赖、返回位置和诊断进度 | 进入/退出诊断、前置依赖已检查、恢复锚点、当前阻塞 | 把学习目标、知识掌握或实践能力塞进结构核 |
| `knowledge` | 找到未验证概念、待解问题、近期错误和相互冲突的理解证据 | 客观题结果、理由追问、概念辨析、具体错误推理、前置知识证据 | 把接触过当成掌握；用一次普通答错固化具体误解 |
| `human` | 调整交互长度、表达方式、难度感受和支持强度 | 用户明确反馈、持续负荷信号、某种呈现方式反复有效或无效 | 从分数推断情绪、人格、医学状态或固定学习风格 |
| `value` | 判断本轮诊断服务于什么目标、优先级和期望产物 | 目标候选、目标澄清、明确确认、兴趣和相关性理由 | 用模型猜测替代用户确认；把目标放进 Knowledge Kernel |
| `practice` | 判断需要识别、解释、应用还是迁移层面的任务，并追踪独立性 | Attempt、辅助等级、代码测试、实践产物、重做和迁移结果 | 把有提示成功等同独立能力；只靠选择题宣称实践能力 |

模块应允许一次交互同时产生面向多个 Kernel 的事件证据，但每个目标都要有独立理由。例如，用户独立完成一个与目标相关的新场景任务，可以同时支持 `knowledge` 和 `practice`；它不能因为“做对了”就顺带写入 `human`。

建议在模块边界定义一个版本化的五核读取包和一个事件输出包。字段名称可以调整，但语义应完整：

```json
{
  "kernel_context": {
    "scope": {
      "learner_id": 1,
      "project_id": 2,
      "checkpoint_id": 3,
      "session_id": 4
    },
    "projection_version": "可选；若现有接口不支持可提出扩展",
    "relevant_projection": {},
    "recent_evidence": [],
    "uncertainties": [
      {
        "kernel": "knowledge",
        "subject": "具体概念",
        "reason": "只有自述，没有评分证据",
        "priority": 0.9
      }
    ]
  },
  "event_proposal": {
    "event_type": "已登记的重要事件",
    "scope": {},
    "payload": {},
    "kernel_targets": ["knowledge", "practice"],
    "evidence_role": "graded_attempt",
    "confidence": 1.0,
    "client_event_id": "稳定幂等键",
    "artifact_refs": [],
    "provenance": {
      "question_id": "冻结后的题目 ID",
      "question_version": "v1",
      "grading_version": "v1",
      "policy_version": "v1"
    }
  }
}
```

`event_proposal` 不是 KernelMutation，也不允许携带未经 Reducer 审核的任意 `short_term` 或 `long_term` patch。运行时应通过统一 `record_event()` 追加事件，再由确定性 Reducer 决定实际核变化。

## 5. 设计自主权

你可以自主选择和组合：

- 对话、问卷、选择题、开放题、代码题、情境任务或微型实践；
- 固定题库、模板生成、LLM 候选生成、检索增强或混合生成；
- 启发式选题、信息增益、知识追踪、能力分层、IRT/BKT 或其他适当方法；
- 固定流程、自适应状态机、动态停止或分阶段诊断；
- 独立页面、Tutor 卡片、侧边抽屉、项目创建步骤或嵌入式工作台；
- 服务边界、内部模型、表结构、缓存和队列方式；
- 问题数量、追问预算、置信阈值和停止条件；
- 对现有工具、产品技能、工作台和重要事件注册方式的改进建议。

不要求预先采用特定算法或固定接口名称。最终方案只需证明：为什么这样能够更快、更准地获取信息，并且可以可靠接入 LearnFlow。

## 6. 不可绕过的架构边界

1. 不直接写入 `KernelState`；状态变化必须先形成登记过的 `EvidenceEvent`。
2. 生成的题目、讲解和画像文本本身不是学习证据。
3. 一次答对不能直接升级为稳定掌握。
4. 跳过、缺失输入、不会作答和答错必须区分。
5. 有提示或有辅助的成功不能等同于独立成功。
6. 不因为答错就推断焦虑、注意力不足、固定学习风格或其他 Human Kernel 结论。
7. LLM 的无依据判断不能直接改变长期记忆、掌握状态或确定性教学策略。
8. 所有读取和提交必须验证 learner/project/checkpoint/session ownership。
9. 重复请求不能重复计分、重复生成 Attempt 或重复写证据。
10. 外部工作流只能返回经过校验的 artifact、候选观察或 EvidenceEvent 输入，不能直接写五核。
11. 追问必须有预算和停止条件，不能形成无界循环。
12. 摸底阶段的追问不得提前泄露答案，避免污染之后的诊断证据。

如果合理创新需要扩展现有注册表、事件 schema 或 Reducer，可以提出并实现带迁移说明和测试的变更；不要通过私有缓存或直接数据库更新绕过问题。

## 7. 希望快速获得的信息

模块应根据当前场景选择最有价值的部分，而不是每次收集全部信息：

- 用户想学什么、为什么学、希望得到什么结果；
- 用户明确自述的经历、基础和限制；
- 目标概念上的实际理解和辨析能力；
- 典型错误、错误理由和潜在前置缺口；
- 能否从识别答案进一步做到解释、应用和独立实践；
- 面对新题型或新场景时是否能够迁移；
- 用户明确表达的难度、节奏、形式和支持偏好；
- 当前证据是否足够进入学习、需要继续了解，还是应开始纠错。

模块不必一次解决完整画像。它可以先交付局部高置信度信息，再在真实学习中继续补全。

建议进一步按职责裁剪上下文：

| 组件 | 适合获得的信息 | 通常不需要的信息 |
|---|---|---|
| 问题生成 | 目标、concept、前置依赖、难度范围、来源、已见题和 seed | 无关项目记忆 |
| 问题校验 | 冻结后的题目规格、答案规则、来源和测试 | 学习者偏好和预期水平 |
| 判题 | 冻结题目、Submission、测试输出和 Rubric | 用户画像、目标掌握等级 |
| 追问决策 | 判题结果、证据缺口、已有追问和剩余预算 | 改写掌握结论的权限 |
| 表达渲染 | 已决定的追问目的、允许引用的证据和表达偏好 | 改变评分或流程阶段的权限 |
| 聚合评估 | 本轮已评分事件、独立性、concept 映射和来源 | 直接写五核的权限 |

## 9. 对外结果的语义要求

内部实现和具体 schema 由你决定。对外边界至少要能表达以下信息：

```json
{
  "session": {
    "id": "discovery-session-id",
    "status": "active|completed|insufficient_evidence",
    "seed": 20260811
  },
  "next_interaction": {
    "kind": "question|clarification|reasoning_probe|task|complete",
    "purpose": "本轮希望降低的具体不确定性",
    "content": {}
  },
  "observations": [
    {
      "kernel": "knowledge",
      "subject": "具体概念或任务",
      "claim": "本次交互实际支持的观察",
      "status": "candidate|supported|verified_once",
      "confidence": 0.8,
      "evidence_refs": []
    }
  ],
  "uncertainties": [],

```

这只是语义示例，不要求照抄字段。实现需要同时产生或触发规范化 EvidenceEvent，而不是把 `observations` 当成直接 Kernel patch。

## 10. 生成、校验与判题

- LLM 可以生成候选题，但候选必须通过独立 Validator 才能展示。
- 每道可评分题应绑定明确的 concept、能力目标、答案规格和来源。
- 选择、数值、结构化输出和代码题应尽可能使用确定性评分。
- 代码题应使用沙箱测试、结构检查或其他可复现验证。
- 开放题可以使用 LLM 提取证据，但必须保留 Rubric、原始回答、置信度、模型和 prompt/策略版本。
- 无法可靠判断时应返回 `needs_review`、`insufficient_evidence` 或继续追问，而不是强行二分正确与错误。
- 错误选项映射通常只能形成 misconception candidate；明确错误推理或重复证据才能提高置信度。
- 题目校验失败时要有安全回退，不能把不完整题目推给用户。
- 同一 seed、相同输入和相同版本应尽可能支持确定性回放。

## 11. 追问与停止

追问可以采用你认为更好的分类，但必须能区分不同证据意义。例如：

- `clarification`：输入缺失、格式错误或题意理解不清；通常不计为能力证据。
- `reasoning_probe`：答案已提交，但错误理由或思路不明确。
- `prerequisite_probe`：需要确认错误是否来自前置知识。
- `state_check`：用户主动表达困难、节奏或形式偏好后进行简短确认。
- `teaching_prompt`：已经进入教学阶段，不再属于纯摸底证据。

LLM 可以负责自然、友好的措辞，但是否追问、追问目的、预算、状态跳转和停止条件必须可记录、可解释。允许使用确定性规则、统计策略或带版本的自适应算法，不要求所有决策都由硬编码规则实现。

需要支持提前结束：当重要问题的证据已经足够，继续提问的收益低于用户成本时，应进入学习或等待真实实践补证，而不是完成预设题量。

## 12. 五核事件交互

你可以自主提出事件集合。合并前，每个影响学习状态的重要事件都必须在可执行注册表中说明：

- 稳定事件 ID；
- 所属 capability、Tool、Agent 和 Workbench；
- learner/project/checkpoint/session scope；
- evidence role 和 confidence；
- 目标 Kernel；
- 幂等键；
- provenance；
- 是否允许参与长期巩固；
- 对应的确定性 Reducer 规则。

典型阶段可能包括目标澄清、诊断启动、题目展示、答案提交、判题完成、跳过、追问、追问回答和诊断完成。具体是否拆分、如何命名由最终方案决定，不必为了匹配这份示例而制造多余事件。

可以在模块变更中提出并实现所需 Reducer 规则，但必须把这类架构交叉修改单独列出，并提供事件到 KernelMutation 的测试。不得改变现有五核的核心语义。

五核集成不能只测试“事件成功写入”。至少验证：

1. 模块读取的是当前 learner 与业务 scope 下的投影，不能串用其他学习者或项目状态。
2. 每类重要交互都先形成 EvidenceEvent，再产生 KernelMutation。
3. Reducer 只修改事件契约允许的 Kernel，并保留 before/after version、reason 和 evidence ref。
4. 诊断模块不会直接修改 `short_term`、`long_term`、`confidence` 或长期掌握数据。
5. 新投影能够影响下一轮选题、追问或停止决定，形成真正的闭环，而不是只做单向回写。
6. 低置信度候选、已验证证据和未知状态在五核投影中保持可区分。
7. 同一 `client_event_id` 重放时不会再次改变任何 Kernel 版本。
8. 归档、纠正或后续相反证据出现后，模块能够读取新状态并调整判断。

## 13. Evidence 判断原则

至少区分：

| 证据类型 | 默认意义 |
|---|---|
| 用户自述 | 目标、经历或偏好的候选/确认信息，不自动证明能力 |
| 内容接触 | 说明看过或听过，不说明掌握 |
| 跳过 | 说明本轮未作答，不自动等于知识错误 |
| 辅助后成功 | 支持“在帮助下可以完成” |
| 单次独立成功 | 支持 `verified_once`，通常不足以长期巩固 |
| 多个独立任务成功 | 可提高稳定掌握置信度 |
| 新场景迁移成功 | 高价值的 Knowledge/Practice 证据 |
| 明确错误推理 | 可支持具体 misconception candidate |
| 重复错误模式 | 可提高误解判断置信度 |
| 明确偏好反馈 | 可进入 Human Kernel 短期观察 |
| 多次有效/无效教学结果 | 可支持偏好巩固，但仍需保留上下文 |

应保留形成结论所依赖的 Attempt、测试、原始回答、来源和事件引用，使之后的 Memory Graph 和用户纠正机制能够工作。

## 14. 质量目标

最终方案应通过实现和评测说明以下问题：

1. 第一次有效回答后，能否立即形成至少一条有限、可追溯的观察？
2. 系统是否会根据已有证据改变下一次交互，而不是固定播放题单？
3. 是否能够在证据足够时提前结束？
4. 是否能够明确返回未知和证据不足？
5. 判题和重要状态跳转能否重放或解释？
6. 重复提交是否完全幂等？
7. 断网、无模型或外部工作流失败时能否安全降级？
8. 相同 seed 是否能稳定演示相同闭环？
9. 所有状态判断能否追溯到具体回答、测试、行为或用户确认？
10. 用户能否理解为什么系统问这个问题，以及系统目前了解到了什么？
11. 是否避免建立与五核竞争的第二画像权威？
12. 是否能把结果直接用于后续路线、教学、练习或 Remediation，而不需要人工翻译？
13. 五核中的证据缺口是否真实影响了下一题或下一次追问？
14. 新事件被 Reducer 处理后，模块是否基于更新投影重新决策？
15. 是否分别证明了对 `structure`、`knowledge`、`human`、`value`、`practice` 的正确读取、回写和禁止写入场景？

速度和准确性需要通过一个小型 seeded eval 集展示。评测可以由你设计，但至少覆盖：基础明显、知识分布不均、连续跳过、含糊回答、辅助后答对、开放题无法可靠评分、重复提交、状态被后续证据纠正等场景。

## 15. 离线与比赛演示

提供一条一键可运行的 seeded demo：

- 无外部 API Key、无网络也能运行；
- 题目、学习者回答和预期事件链可重复；
- 能展示至少一次动态选题或有理由的追问；
- 能展示一次证据不足或未知状态；
- 能展示诊断结果进入 Evidence Ledger，再由 Reducer 更新五核投影；
- 能从 UI 或验收输出看到证据引用和下一步教学建议；
- 演示数据与真实数据明确隔离，可重复重建；
- 比赛文档说明启动命令、演示脚本、预期结果和离线限制。

## 17. 工作方式

先理解现有实现和参考仓库，再自主形成方案并直接推进。不要因为非关键细节缺失而停下来等待确认；在不违反架构边界的前提下作出合理决定，并在设计说明中记录。

如果存在多个可行方向，优先选择能够最快形成可运行证据闭环、同时保留未来替换空间的方案。不要为了展示复杂算法牺牲可验证性和用户体验，也不要为了快速完成退化成固定问卷。

最终交接时，请明确说明：

- 你选择了什么方案，为什么；
- 哪些判断是确定性的，哪些是概率性的；
- 哪些数据是事实、候选观察或未知；
- 模块分别读取了哪些五核字段，为什么需要；
- 发出了哪些事件；
- 每个事件目标是什么 Kernel，Reducer 如何处理，如何影响下一轮决策；
- 如何运行测试、eval 和 seeded demo；
- 哪些设计值得下一阶段继续实验。

## 18. 最终原则

这项工作的核心不是做出一份更复杂的画像，而是建立一个高信息增益、低打扰、可持续纠正的学习者状态发现能力：

> 模块负责获得可靠证据，五核负责保存和组织证据，后续教学负责使用证据。
